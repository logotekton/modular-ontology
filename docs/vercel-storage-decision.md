# Vercel 스토리지 아키텍처 결정 기록 (2026-07-08)

## 문제

Vercel 서버리스에서 `DATA_DIR`은 `/tmp`(컨테이너별, 콜드 스타트마다 초기화)다.
동기화가 만드는 모든 상태 — 증분 파일 캐시, 팩 zip, SQLite 인덱스 — 가 영속되지
않아, 배포 환경에서 동기화를 돌리면 매번 제로부터 풀 다운로드가 시작되고 함수
시간제한(504)에 걸려 끊기는 루프가 됐다 (동기화 딥리뷰 최상위 발견).

PR #7로 배포 환경 동기화는 즉시 400("로컬 서버에서 동기화하세요")을 반환하도록
가드했고, status 엔드포인트가 `persistentStorage: false`를 노출한다.

## 현재 동작 (가드 이후)

- **동기화·재색인·write-back**: 로컬 uvicorn에서만 실행. 결과는 Drive write-back
  (DB 파일 + 팩)으로 공유된다. Drive가 사실상의 영속 원본(source of truth).
- **Vercel(조회)**: 콜드 스타트 시 `ensure_runtime_registry()`가 Drive에서 DB·팩을
  `/tmp`로 내려받아 서빙한다. 첫 요청이 느리고(수 초~수십 초), 인스턴스가 재활용되면
  반복된다 — 하지만 데이터 유실은 없다.

## 옵션 비교

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 현상 유지 | 로컬 동기화 + Drive 원본 + Vercel 조회 전용 | 비용 0, 이미 적용됨 | 콜드 스타트 첫 요청 느림 |
| B. Vercel Blob/S3 미러 | DATA_DIR을 오브젝트 스토리지에 미러 | Vercel 네이티브 | SQLite는 오브젝트 스토리지에서 직접 못 씀 → 결국 요청 시 다운로드 = A와 동형, 실익 미미 |
| C. 관리형 DB 전환 | SQLite → Turso(libSQL) 또는 Neon(Postgres), 팩 zip은 Drive 유지 | 진짜 영속, 콜드 스타트 페널티 제거 | store.py/pack_index.py의 SQL 계층 이관 작업 (libSQL이면 소규모) |
| D. 상시 서버 이전 | Vercel → Fly.io/Railway (볼륨 지원) | 코드 거의 무변경, 동기화도 배포 환경에서 가능해짐 | 호스팅 이전 작업, 월 비용 소액 |

## 권고

1. **단기 (적용 완료)**: 옵션 A. PR #5/#7/#9 이후 로컬 동기화는 증분·병렬로 빨라졌고,
   배포 환경은 명확한 안내로 오동작하지 않는다.
2. **중기**: 배포 환경에서도 동기화가 필요해지는 시점에 **옵션 D(Fly.io 볼륨)** 우선
   검토 — 전체 코드가 파일시스템 전제라 이관 비용이 가장 낮다. DB만 먼저 풀고
   싶다면 옵션 C(Turso)가 차선.
3. B는 채택하지 않음 (구조적 이점 없음).

## upload_pack 강제 동기화 정책 (오너 판단 항목 — 결론)

`upload_pack`은 업로드 수락 전 `run_google_drive_sync(force=True)`를 실행하며,
테스트(`test_pack_upload_is_session_admin_only_and_accepts_valid_zip`)가 이를
의도된 동작으로 명시한다(업로드 직전 Drive 상태 최신화로 충돌 방지).

**결론: force=True 유지.** 근거 — PR #5 이후 변경 없는 강제 동기화는 다운로드·
재색인·write-back을 전부 건너뛰어 순수 폴더 리스팅만 남고, PR #9의 병렬 워크·
커넥션 재사용으로 그 리스팅마저 짧아졌다. 정책을 바꿔 얻는 이득이 사실상
사라졌으므로 테스트가 못박은 안전한 의미론을 유지한다.
